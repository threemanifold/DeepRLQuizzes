# AReaL: A Large-Scale Asynchronous Reinforcement Learning System for Language Reasoning
arXiv 2505.24298 (notes from HTML v5). Appendix details marked [unverified] came from a summary only.

## Architecture (Sec 4.1): relevant to Q47, Q48, Q54, Q55
- Components: Interruptible Rollout Worker (`generate`, `update_weights`), Reward Service, Trainer Workers, Rollout Controller.
- `update_weights` interrupts ongoing generations. Workers DISCARD KV caches computed with old weights, RECOMPUTE them with new weights, then keep decoding.
  -> one trajectory can contain segments from several policy versions (Sec 4.2 "Inconsistent Policy Versions").
- Proposition 0 (Appendix D calls it Prop 1): a sequence generated by (π_θ, …, π_{θ+k}) with segment boundaries 1 = t_0 < … < t_{k+1} = H
  is equivalent to sampling from some single π_behav (piecewise over disjoint state sets).
- Replay buffer: "data from the replay buffer is used only once" (for freshness). Trainers take the oldest trajectories first.
- Rollout and training are fully decoupled. Generation is throttled because excess data is stale and goes unused (Sec 7.3).
- Sec 5.2: token probabilities are recomputed when the global batch arrives (this gives π_prox).

## Staleness control (Sec 5.1, Eq. 3): Q49–Q53, Q57
- η = maximum permitted staleness in each training batch. η = 0 is synchronous RL.
- Eq. (3): ⌊(N_r − 1)/B⌋ ≤ i + η, where N_r is the total number of generated trajectories, B the batch size per step and i the current policy version.
  The controller checks it when submitting new generation requests and rejects requests that would violate it. This rate-limits how far generation runs ahead.
- (The quiz uses ⌊N_r/B⌋ ≤ i + η.) It bounds the version gap measured at request submission. It is not a per-token age bound.
- Small η can slow generation when long trajectories are in flight; the authors suggest a large η for throughput.
- Experiments: η = 4 for coding, η = 8 for math. 3/4 of the devices do inference, 1/4 do training.
- Sec 7.4: moderate staleness (η ≤ 8) has minimal impact on final performance with the decoupled objective. η → ∞ is worse than the η = 0 oracle even with decoupling.
- Table 2 (1.5B math, AIME24, without → with decoupled): η=0: 42.0; η=1: 41.8→42.1; η=2: 40.0→41.8; η=4: 23.3→42.2; η=8: 35.7→41.0; η=16: 35.8→38.7; η=∞: 34.0→36.9.

## Decoupled PPO (Sec 3.1, Sec 5.2): Q56, Q57, Q76
- Eq. (2) standard PPO: u_t(θ) = π_θ/π_old, clipped at 1 ± ϵ.
- Eq. (4): J(θ) = E_{a_t∼π_behav}[ Σ_t min( (π_θ/π_behav) Â_t, (π_prox/π_behav)·clip(π_θ/π_prox, 1−ϵ, 1+ϵ) Â_t ) ].
- Eq. (5): J(θ) = E_{π_behav}[ Σ_t (π_prox/π_behav) · min( u^prox_t Â_t, clip(u^prox_t, 1−ϵ, 1+ϵ) Â_t ) ], where u^prox_t = π_θ/π_prox.
- π_behav is the sampling policy. π_prox is the trust-region centre: the parameters before each model update step, with token probabilities recomputed by the trainer.
  Hilton et al. (batch-size invariance) used an EMA of the parameters for π_prox, which is too expensive for large reasoning models.
- The weight π_prox/π_behav is NOT clipped or truncated in the paper. It is a plain importance weight.
- Why not anchor on π_behav: it pulls π_θ back toward old, lower-quality policies and slows improvement. With stale data, the ratio π_θ/π_behav can already lie outside [1−ϵ, 1+ϵ] before any update, so the gradient becomes zero or the update is badly constrained.
- What limits the mismatch: the staleness bound η (Eq. 3), single-use FIFO-ish consumption (oldest first), and interruptible generation (new weights are adopted mid-generation, so the tails of trajectories are fresher). The decoupled objective itself does not bound π_prox/π_behav.
- Naive PPO under staleness fails to match the oracle (wrong clipping centre plus policy changes during interruptible generation). With decoupling, training is >2× faster.

## Speed / system (Sec 6, 7)
- Up to 2.77× vs synchronous AReaL (1.5B: 41.0 h → 14.8 h). Table 1 also has 7B (57.7 → 25.4 h), 14B code (48.8 → 21.9 h) and 32B code (51.1 → 31.1 h).
- Dynamic microbatching: padding-free packing under a 32,768-token budget per microbatch, versus a baseline of 32 fixed microbatches. About +30% throughput.
- Interruptible generation: +12% (1.5B) and +17% (7B) throughput, because the controller no longer waits for the longest response.
- [unverified] App B.1: reward ±5, 512 prompts × 16 answers, 4 minibatches, ϵ = 0.2, GAE λ = γ = 1, lr 2e-5, max generation length 27648.
